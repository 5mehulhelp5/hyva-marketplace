# Tailwind CSS v3 → v4 migration (Hyvä theme)

Drives the Tailwind v3→v4 switch of a Hyvä theme (and `app/code`): runs the official Hyvä engine, then
**finalizes** — **re-homes and migrates every custom CSS file into the standard Hyvä tree**
(`base/`/`components/`/`theme/`/`utilities/`), consolidates the design tokens into a single source
(`hyva.config.json`), keeps `web/tailwind` a full vendor copy, verifies the build. Beyond mere class
renaming: file **placement & organization**, SCSS, `@layer`→`@utility`, `theme()`→`var()`,
`addUtilities` plugin, changed defaults. Works whether the child theme is still on v3 **or already on v4
but not finalized** (custom CSS mis-organized, tokens not single-sourced). Discovers the environment
dynamically. **No hardcoded paths.**

## Guardrails (NON negotiable)
- **Runtimes via the project runner.** `node`, `npm`, `npx`, `composer` run inside the PHP container through `$HYVA_RUNNER` (see "Runner" below), never on the host.
- **No git.** No `git add` / `git commit` commands — the user manages history.
- **Official Hyvä tools `--dev`**, never in production.
- **Keep the backups** generated by the official tool until QA sign-off.
- **Inline human gate**: the review of migrated custom styles always happens in conversation.

## Runner
`$HYVA_RUNNER` = the command that runs a runtime (`node`, `npm`, `npx`, `composer`) **inside the project's PHP
container**. **Invoked by `hyva-upgrade`**: inherit the value already resolved by the orchestrator.
**Standalone**: resolve it yourself — Warden (default) `warden env exec php-fpm`, or Docker
`docker compose exec -T <php-service>` (`-T` required, no TTY here). Export it before running this skill's
scripts (they default to Warden): `export HYVA_RUNNER="…"`.

## Two operating modes

### Invoked by `hyva-upgrade` (Phase 6)
Receives in context: `THEME` (theme root), shared `WORKDIR` (`var/hyva-upgrade/<ts>/`),
additional sources (`app/code`), and the already-collected breaking-change context. Runs the official
engine (step 1) then the full Finalize step (A/B/C + D/E) — **Tailwind only** (CSS, tokens, scan config;
`.phtml` touched solely for class renames). Trimming templates to overrides-only is the orchestrator's
job (Phase 5), not this skill's. Writes its artifacts (`tw-custom.tsv`, backups) into the shared `WORKDIR`. **Does NOT do the
rebuild** (deferred to Phase 7 of the orchestrator); E's build-output items run after that rebuild.

### Standalone
No `WORKDIR` provided:
1. Creates its workdir: `var/hyva-tailwind-v4/<timestamp>/`.
2. Discovers the theme(s) (reuse `hyva-theme-list` if available, otherwise look for a
   `web/tailwind/tailwind.config.js` under `app/design/frontend/*/*`).
3. Checks the state and picks the entry point (default-theme **≥ 1.4.0** is the baseline):
   - **Child theme still on v3** — a `web/tailwind/tailwind.config.js` is present → run the **full**
     procedure (engine step 1 → Finalize step 2 → rebuild step 3).
   - **Child theme already on v4 but NOT finalized** — no `tailwind.config.js`, yet finalize symptoms
     remain: `generated/tailwind.config.css` present, a hand-maintained `@theme` living in `generated/`,
     placeholder brand tokens, or custom CSS sitting in non-standard folders (`site/`, `components/style/`,
     `_`-prefixed files, grab-bag files) → **SKIP the engine (step 1)** and go straight to **Finalize
     (step 2)**. There is no backup here, so step B works from the **live `web/tailwind`** (see B).
   - **Already v4 AND finalized** — single token source, custom CSS organized in the standard tree →
     nothing to do; explain and stop cleanly.
4. Runs the resolved path, **rebuild included** (step 3), and E's build-output items after it.

## Procedure
> Full detail: `references/migration-procedure.md`. Transform catalogue:
> `references/tailwind-v4-breaking-changes.md`.

1. **Official Hyvä engine**: `scripts/run-tailwind-v4-migration.sh <THEME>`. Backs up `web/tailwind`
   to `web/tailwind.backup.<date>`, **copies the vendor v4 `web/tailwind` over it**, converts the config
   to CSS v4 (usually `generated/tailwind.config.css`). Do NOT use `npx @tailwindcss/upgrade` nor
   `find-deprecated-classes.js` (see the procedure). ⚠️ After this, the theme's `web/tailwind` **is** the
   vendor copy — the custom CSS lives only in the backup, the converted config lands (wrongly) in `generated/`.
   ⚠️ **Never run the engine on a theme already on v4** (no `tailwind.config.js`, no backup): it would
   back up your *live* custom CSS and overwrite `web/tailwind` with a fresh vendor copy — destructive and
   pointless. Such themes skip straight to Finalize (step 2), working from the live tree.
   - 1bis. **Drift sentinel** (recommended): `scripts/check-deprecated-drift.sh` — alerts if Hyvä has
     added deprecated classes not covered by `references/renamed-classes.tsv`. Run it when bumping
     `upgrade-helper-tools`.
2. **Finalize & migrate styles** — the migration is NOT done until this is. **A/B/C core, D/E recommended**;
   **A is interactive** (ask before a shade not in the brand palette):
   - **A. Consolidate tokens into a SINGLE source: `hyva.config.json` `tokens.values`.** Move the design
     tokens there (color scales, breakpoints, fontSizes, spacing, radius, shadows, tracking, leading,
     fonts), **dropping what v4 provides natively**. The **`@utility` plugins + animations
     (`--animate-*` + `@keyframes`) are NOT tokens** → move them into files under `utilities/`. Drop the
     `@import ".../generated/tailwind.config.css"`, that file, and (if still present) the dead `tailwind.config.js`.
     **Remap the WHOLE semantic set** to the brand palette (primary/secondary triads,
     on-primary/on-secondary, all `--form-*` incl. `--form-active-color`, `accent-color`) — not just
     `--color-primary`. Namespace = `--color-*` **singular** (never `--colors-*`). Verify the
     **browser-computed** color, not the source. *(ask before an off-palette shade)*
   - **B. Re-home AND migrate every custom CSS file into the standard Hyvä tree.** Two duties — **do not
     skip the first**; it is the one the syntax scan can't do for you and the one most easily forgotten.
     - **Source.** The custom CSS lives either in the backup (`web/tailwind.backup.<date>`, when the
       engine ran) **or — if the theme was already on v4 (no backup) — in the live `web/tailwind` itself**,
       mis-organized in place. Either way it is your input. *Never conclude "no backup → nothing to do":
       the live tree is the source, and re-homing it is exactly this step's job.*
     - **B1 — structural / placement audit (active judgment; the scan does NOT do this).** The scan below
       finds only **syntax** — it will never tell you a file is mis-placed or does five things at once. So
       read the custom tree and **reorganize it into the standard Hyvä layout**: `base/` (element styles,
       fonts), `components/` (reusable component classes, **one concern per file**: `button.css`,
       `forms.css`, `card.css`…), `theme/` (page/section-specific), `utilities/` (`@utility` helpers,
       animations). Fix these smells: non-standard subfolders (`components/style/`) → flatten; SCSS-style
       names/dirs (`site/` folder, `_name.css` prefixes) → plain files in the right folder; grab-bag files
       (buttons + forms + layout + scrollbars in one file) → split by concern; custom code in the wrong
       folder or wrong `@layer` (component classes parked in `@layer base`); bespoke button classes →
       Hyvä `btn`/`btn-primary`/`btn-size-*`. When relocating, **preserve the cascade** (keep each rule's
       `@layer`/order so precedence doesn't shift) and **verify the compiled `styles.css` is
       behavior-equivalent before/after** (same declarations & selectors). Moves that touch many `.phtml`
       (e.g. adopting `btn`) are a real refactor → flag & gate, don't rename blindly.
     - **B2 — syntax migration (scan-driven).**
       `TW_DIR="<backup-or-live-web/tailwind>" scripts/scan-tailwind-v4-custom.sh <THEME> "" app/code > "$WORKDIR/tw-custom.tsv"`.
       Apply the tiers (`auto-safe` deterministic / `needs-review` = 1 subagent per file): `theme()`→`var()`,
       renamed/scale-shift classes, `bg-[--x]`→`bg-(--x)`, `!important` suffix (`w-full!`), `@import`
       relative, `@screen`→media, `*-opacity-*`→slash, `@layer`→`@utility`, plugin→`@utility`, de-SCSS,
       `@reference` in isolated `@apply` files.
     - **Merge rule.** For each file: **merge your custom into the matching native file** (same name — or a
       differently-named file playing the same role — **never keep both**), or **add a new custom file** in
       the right folder; **discard pure vendor copies**. No two files doing the same thing.
     🔲 **Gate: review of migrated custom styles.**
   - **C. CSS stays a FULL vendor copy + configure the scan (Tailwind only).** `web/tailwind` keeps the
     SAME files as the new vendor v4 (content overridden + custom additions); **never delete a CSS file
     identical to vendor** — it is compiled, not inherited, so deleting breaks the build. Configure the
     parent scan (`hyva.config.json` `tailwind.include`/`src`) + a `.gitignore` **deny-list** (v4
     `@source` respects `.gitignore`). *Out of scope:* trimming templates to overrides-only (deleting
     vendor-identical `.phtml`/`.xml`) → `hyva-upgrade` Phase 5; this skill only renames Tailwind classes
     in `.phtml`.
   - **D.** *(recommended)* Extend the conformance scan to the custom CSS: scale shift
     `rounded`/`shadow`/`blur`, `outline-none`→`outline-hidden`, the border-color shim, arbitrary vars.
   - **E.** *(recommended)* Verification gate: compiled `styles.css` has the utilities used; native
     components branded (rest + hover/active/focus); no build warning (`Unknown at rule: @screen`);
     a **vendor-only** `.phtml` class reaches `styles.css` (proof the parent scan works).
3. **Rebuild**: delegate to the `hyva-compile-tailwind-css` skill (or `$HYVA_RUNNER` in
   `web/tailwind`). **Only in standalone mode** (in invoked mode, the orchestrator rebuilds in Phase 7);
   E's build-output items run after this rebuild.

## Watch-outs
- The config format moves from JS to CSS/variables — review the merge carefully.
- **One token source = `hyva.config.json`** (it regenerates `generated/hyva-tokens.css`); no
  hand-maintained `@theme` left in `generated/`. Two `@theme` blocks (default placeholders vs brand
  values) is the #1 silent regression → verify the **browser-computed** color, not the source text.
- **Keep the backups** (`web/tailwind.backup.<date>`) until QA sign-off — B and C both read them.
- Changed defaults (border `currentColor`, ring, placeholder, button cursor) are **not** detectable
  by the scan (cat. 7 of the catalogue) → visual check in QA.
